# Windows基準版と改善PRの進め方

2026-11-12。まず単独で動くWindows版の基本操作を固め、その基準を保ったまま、小さい改善PRを並行して進める。基準版の範囲は個人用の日単位タスク・予定管理であり、製品全体の将来機能をすべて実装したという意味ではない。

## 基準版の範囲

| 利用場面 | 合格条件 |
| --- | --- |
| 起動と保存 | ビルド済みexeで起動し、ネットワークなしで保存・再起動復元できる。起動入口が開発PCでコンパイルやfixture生成を始めない |
| タスクと予定 | Task・独立Event・Taskに関連するTimeBlockを区別し、追加・編集・完了・削除・所属を操作できる |
| 検索と選択 | 日本語検索、状態・期限・リスト・日付条件を使える。表示から消えたTaskをEnter/F2や遅れて届いた応答で開かない |
| 下書き | 入力不正でも値を残す。未保存の移動には確認を出す。ドラッグの仮配置を手編集した後は、通常の下書きとして保持する |
| 履歴と関連 | 完了で作業枠を消さず、Undo/Redoと再起動後もID・関連・時刻を保つ。古い版による上書きを拒否する |
| 表示 | 1280/900幅とlight/darkで主要な一覧・編集・時刻欄を操作できる。既存の仮想化・DBワーカー・動き軽減を維持する |

合格は、対象のsource SHAに対するremote fmt/Clippy/全テスト/buildと、取得したexeのhashに結び付けた実画面確認で判断する。以前の成功runを、変更後のHEADの成功へ読み替えない。CIのnative GUI `NOT_RUN`と手動確認は別に記録する。具体的な実績はPR本文、Actionsのevidence、[プロトタイプの記録](prototype-status.md)を参照する。

IME変換中、Narrator、全DPI、780px未満のcompact表示、大規模GUIや入力から画面提示までの性能は、少数操作の成功だけで合格にしない。未検証と既知の不具合を区別して残す。

## 最初のPR構成

1. 現行実装と、完成を妨げる再現済みの問題を `prototype/pc-first` で統合し検証する。導入PRのbaseは `main`。
2. 検証が揃った基準tipを固定する。改善ごとに専用branchとworktreeを作り、所有ファイル・合格条件・検証方法を先に決める。
3. 基準版レビュー中の独立改善PRは `prototype/pc-first` をbaseとする兄弟PRにする。基準版のbranchへ後続の改善を混ぜない。
4. 基準版の取り込み後は、祖先関係と差分を確認して子PRのbaseを `main` に移す。squashで祖先が変わる場合は、その改善だけを載せ直す。既に共有した履歴のforce-pushやPRのmergeは、作成の許可と同一視しない。

基準版の導入は既存実装を含むため大きくなるが、以後は一つの問題・改善に一つのPRを基本にする。UI、core、CIを理由なく同じPRへまとめない。改善案だけを増やさず、再現・回帰テスト・動く成果物までを一つの変更として扱う。

## CIと配布

- PRはremote Windowsでfmt・Clippy・テスト・製品build・依存検査を行う。現行設定ではPRから配布exeや本測定を作らない。
- `main` / `prototype/pc-first` のtrusted pushは、full成功後にexeを配布し本測定する。artifactのAPI由来、source、run/attempt、hashを確認してから使う。
- PRのhead SHA、base SHA、実際に検証する合成merge SHAを区別する。PR artifactの自己申告だけで実行物を信用しない。
- `[skip ci]` のHEADを基準版の合格根拠にしない。新しい実装や検証対象のcommitは通常のCIを起動し、該当SHAの結果を確認する。
- 将来main導入前のUI候補を実機確認する場合は、審査した候補をtrustedな統合branchで再検証し、その統合SHAのexeを確認する。PR向けの取得許可を安易に広げない。

開発PCではRust/Cargo/rustfmt/check/test/clippy/bench、fixture生成、重い測定を行わない。ローカルは編集・軽量検査・許可されたビルド済みexeの少数操作に限定する。詳細は[開発手順](development.md)。

## 改善候補の選び方

保存内容や下書きを失う問題、表示と操作対象の不一致を先に直す。その後は、保持期限後のRedoの整合、不要なDB照会、CIの無駄な実行など、根拠と範囲が明確な改善を選ぶ。性能のPRは処理を省いた事実と、時間短縮を実測した事実を区別する。

整合したバックアップ、JSON/ICS入出力、繰り返し、通知、同期、Android、AI/MCPは後続の段階。古い[システム実装計画](implementation-plan.md)にある順序や未実装表記を、現在の完成状態と混同しない。
