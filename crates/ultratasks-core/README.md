# ultratasks-core

GPUI・ネットワークランタイムから独立した、ローカルのタスク／カレンダー操作エンジン。

## 接続

`Engine::open(path)` で開く。親ディレクトリは呼び出し元で用意する。SQLiteの操作は同期的なので、UIからは専用ワーカースレッドへ委譲する。`Engine::in_memory()` はテスト用。

`execute(Command)` が保存・入力検証・更新版照合・操作履歴をまとめて処理する。各コマンドは一つの `BEGIN IMMEDIATE` トランザクションで確定する。書き込みはSQLiteのロックで直列化し、WAL、外部キー検査、5秒のbusy timeout、`synchronous=FULL` を使う。

既存の他アプリのSQLiteファイルは受け入れない。空のDBを初期化する場合はアプリケーションIDとスキーマ版を記録し、再接続時はそれらと必要な列を検査する。DBが別用途・新しい未対応版・不完全なスキーマなら、ジャーナル形式やテーブルを変更する前に拒否する。

## 操作と検索

- `Task`、`TaskList`、`Event`、`TimeBlock`、`Calendar`、`Reminder` はUUID v7ベースの別々の型のIDを持つ。
- 更新・削除には取得時の `revision` を渡す。古い版は `Error::Conflict` になる。
- タスク削除は、そのタスクの作業枠と各対象のリマインダーも同じトランザクションで削除済みへ変更する。予定／作業枠の削除も関連リマインダーを削除し、Undoではまとめて復元する。
- リストに有効なタスクが残っている場合、リスト削除は `ListNotEmpty` になる。
- 削除済み行は復元・将来の同期のために保持する。現段階での完全削除・圧縮のAPIはない。
- `tasks(&TaskQuery)` は日本語の部分一致、完了状態、リストで絞り込む。`%`、`_` はワイルドカードではなく文字として検索する。英字大小の折り畳みはSQLite標準のASCII範囲で、Unicode全体のcase foldingは未実装。
- 検索の取得上限は1〜1000件。タスクは `offset` で追加ページを取得できる。`lists`、`events`、`time_blocks` は現段階では上限付きの取得API。

## 時間の意味

時刻付きの予定・作業枠はUTCの瞬間とIANAタイムゾーンを持つ。終日はローカル日付の範囲を保持する。期限も日付だけの `DueDate::Date` と瞬間の `DueDate::At` を区別する。すべての期間は開始を含み終了を含まない。

`CalendarQuery` はUTCの開始・終了と表示タイムゾーンを指定する。時刻付き予定は実際に重なるもの、終日予定はその表示タイムゾーンで対象になる日付を取得する。1回の期間は最大366日。対応する年はUTC／ローカルとも1〜9999で、うるう秒を含む瞬間は拒否する。

夏時間の欠落・重複するローカル時刻からUTCへの変換は、入力側で明示的に解決する。現在の操作APIは確定したUTCの瞬間を受け取る。繰り返しの展開では下記の明示的な規則を使う。

## 繰り返しとカレンダー

`SetEventRecurrence`／`SetTaskRecurrence` で日次・週次・月次の規則を設定する。タスクの起点は期限、予定の起点は開始日のローカル日付。間隔は1〜10000、任意の `count` は1〜10000、`until` は含む終端日。週次はISO曜日（月曜1〜日曜7）で、起点の曜日を含める。月次は同じ日番号を使い、存在しない日を飛ばす。月末へ丸めない。

時刻付き系列は元のタイムゾーンの壁時計時刻を保つ。夏時間で存在しない時刻は飛ばし、重複時刻は早い方の瞬間を使う。最初の明示的な起点だけは入力された瞬間を保つ。存在しない月日・時刻は `count` を消費しない。時刻付き予定の長さは実経過時間、終日は日数を保つ。

`SetEventException`／`SetTaskException` は元の発生日をキーに今回だけの変更・取消・タスク完了を設定する。移動先が元の日付から遠くても、その移動先のクエリで表示する。`exception: None` で例外を解除する。例外は1系列1000件まで。規則・起点を変える前に例外を明示的に解除し、既存の例外が黙って別の発生回に移らないようにする。系列変更と例外解除は `execute_batch` でまとめられる。タスク本体の完了は系列の既定値で、1回だけの完了には例外を使う。

`event_occurrences(query, calendar_id)`／`task_occurrences(query)` が展開結果を返す。純粋関数 `expand_event`／`expand_task` も同じ計算を提供する。結果が指定上限を超えた場合はエラーを返すため、期間を狭める。元データ用の `events` は系列を展開しない。COUNTなしの系列は問い合わせ期間へ直接進み、COUNTありは最大10000回の有効発生に制限する。

予定は `AssignEventCalendar` で所属先を変更する。予定が残るカレンダーの削除は拒否する。タスク期限の絞り込みは `tasks_due` を使い、日付期限と瞬間期限を区別してからページを切る。日付期限の「期限超過」は指定タイムゾーンのその日が終わってからになる。

リマインダーは `CreateReminder` 等で保存し、`At` は単発の瞬間、`Before` は対象の各発生回からの相対分数。各端末の通知配送記録は同期対象のリマインダー定義と分離する。OS接続と通知の検証条件は通知クレートの資料を参照する。

## 原子的な一括操作と再試行

`execute_batch` は1〜1000コマンドを1トランザクション・1Undo単位にまとめる。途中で失敗すれば保存・履歴・同期送信待ちをすべてロールバックする。`preview_batch` は同じ検証経路を実行して最後に必ずロールバックするため、表示用の提案を保存前に検証できる。

`execute_idempotent(request_id, commands)` はactorごとのリクエストIDで重複作成を防ぐ。同じID・同じ入力は以前の結果、異なる入力はエラー。`execute_idempotent_guarded` は選択中の対象の版を同じトランザクション内で確認する。結果の再取得は版の確認より先に行う。リクエストIDは無期限保持するため再送を安全に扱えるが、履歴1000件とは別にDB容量を使う。完全エクスポート／別DBへのインポートでは履歴とリクエストIDを移行しない。

## Undo / Redo

履歴はDBに保存し、再起動後も使える。1つのactorにつき直近1000操作を保持する。新しい操作を行うと、そのactorのRedo分岐を破棄する。Undo／Redoでも更新版は増加し、古い版を再利用しない。

通常の `open` は `local` という共通の履歴actorを使う。独立した編集主体は `open_for_actor(path, actor)` で別actorを指定する。actorは履歴の区分であり、認証やアクセス制御ではない。同じactorを使う接続は同じUndo履歴を共有する。

Undo／Redoは対象行の現在の版・内容・関連を検証する。他actorの新しい編集や、復元先の削除、別actorが追加した子要素があれば `HistoryConflict` として原子的に拒否する。同じ値を書き直した別actorの変更も版の境界として保持する。`history_status` のフラグは履歴の有無であり、現在の競合を考慮した成功保証ではない。

## ファイル構成

- `model.rs`: 公開する型・コマンド・クエリ。
- `engine.rs`: 操作、入力検証、履歴、関連の整合性。
- `storage.rs`: SQL、マイグレーション、行の変換。
- `recurrence.rs`: タイムゾーンを含む繰り返しの純粋計算。

現在のデータを正とする通常のSQLite保存であり、起動時に全履歴を再生する構成ではない。同期は `sync.rs`、入出力・復元は `transfer.rs`／`ics.rs`、MCP・AIは別ホストから共通コマンドへ接続する。
