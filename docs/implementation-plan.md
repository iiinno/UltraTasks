# システム実装計画

2026-11-09。ローカルコアとGPUI仮アプリの初期実装を追加した。Task / TaskList / Event / TimeBlock、SQLite、基本検索、更新版の照合、永続Undo/Redoを実装し、Linux上でテスト・GUI操作を確認している。Windows実機とAndroidは未検証。各段階の項目は計画であり、一括して実装済みという意味ではない。

現在の不足: Calendarの所属先管理、期限による絞り込み、繰り返し、入出力、バックアップ、通知、同期、MCP・AI。仮画面はタスクと作業枠が中心で、Event / TaskListの全編集UIは未接続。[開発と検証](development.md)と[Androidの調査](android-spike.md)も参照する。

## 今回の方針変更

システムを先に実装する。UIの監修・仕上げはユーザーが後から行う。仮UIは編集しやすい簡単な構成とし、GPUIの入力・描画・性能を確かめるために使う。画像案の承認や完成したデザインシステムを、コア実装の前提にしない。

Rust、GPUI、WebViewなし、WindowsとAndroid、ローカル完結、任意のセルフホスト同期という製品方針は維持する。

## ユーザー回答で確定したこと

| 判断 | 決定 |
| --- | --- |
| 利用範囲 | まず個人用、自分の複数端末。共有・担当者・チーム権限は後から |
| 外部カレンダー | まずUltraTasks単体。入出力を用意し、Google Calendar等との常時連携は後から |
| 同期サーバーの信頼 | 自分のサーバーは内容を読める設計でよい。通信保護と認証を優先し、E2EEは初期要件にしない |
| UI | 後からユーザーが監修。現在は単純で変更しやすい仮画面を作る |
| アニメーション | GPUI実装と性能確認用に最低限を仮実装する |

以下の構成・実装順・細かな振る舞いは、この決定に基づく開発側の提案。ユーザーがすべての細部を指定済みとは扱わない。

## 小さく始める構成

```text
crates/
  ultratasks-core/
    src/
      model/          Task・Event・TimeBlock、型と不変条件
      application/    commands・queries、履歴とUndo
      calendar/       日付・タイムゾーン・繰り返し
      storage/        SQLite、トランザクション、マイグレーション
      transfer/       エクスポート・インポート
apps/
  desktop/
    src/
      views/          GPUIの画面と部品
      presentation/   選択・編集中・スクロール等の表示状態
      theme/          色・余白・文字・モーション設定
      platform/       OS通知等の接続先
```

初期はcoreとdesktopの2クレート。Androidの最小ホストは早期検証用に追加する。同期サーバーとMCPアダプターは各段階で追加し、先に空のクレートを並べない。

coreはGPUIに依存せず、テストや計測プログラムから直接操作できる。`model`と`calendar`の計算はDB・ネットワーク・描画から独立させる。SQLiteはcore内の専用モジュールに閉じ込める。実際に複数の実装が必要になるまで、DB抽象化やプラグイン基盤を増やさない。

UIは作成・更新・完了・削除・時間割り当て等の操作APIと、期間・件数を絞れる検索APIを呼ぶ。SQLや繰り返し計算を画面に書かない。APIは構造化した結果とエラーを返し、表示文言・色・アニメーションの判断はUI側が持つ。

SQLite処理はバックグラウンドの専用処理へ寄せ、書き込みを直列化する。データ変更と必要な操作記録は一つのトランザクションで確定する。画面へ変更したID等を通知し、毎回全データを読み直さない。編集中・保存待ち・保存失敗を区別し、保存完了前に永続化済みと表示しない。

候補はSQLiteと`rusqlite`、型付きID、`serde`、実績のある日付・タイムゾーン・繰り返しライブラリ。採用版とAndroid互換性は実装開始時に検証し固定する。Webサーバーが必要になる段階でHTTPランタイム等を追加する。

## データの意味

- **Task**: 終わらせる仕事。タイトル、完了状態、所属リスト、任意の期限などを持つ。期限は日付だけの値と時刻付きの値を区別する。
- **Event**: 時間または日付が決まった予定。終日の日付範囲と、時刻付き予定を区別する。
- **TimeBlock**: Taskへ割り当てた作業時間。一つのTaskに複数持てる。Taskを時間軸に置いても別Taskを作らない。
- **List / Calendar**: タスクや予定の所属先。個人用途から始め、共有権限や担当者を初期必須フィールドにしない。

共通のID・更新版・削除記録を用意する。端末時計の新旧を更新競合の唯一の根拠にしない。Task完了とTimeBlock削除を混同せず、Task削除時の関連処理は原子的な操作として仕様化する。

終日は日付と終了境界を保存し、UTCの深夜へ置き換えない。時刻付きの単発予定は瞬間とタイムゾーン、繰り返し予定は元のローカル時刻・タイムゾーン・規則・例外を区別する。期限、開始、作業時間は別概念とする。

## 実装順と完了条件

### 0. ビルドと検証の土台

- Rust workspace、依存固定、整形・静的検査・coreテスト用CIを用意する。
- テスト用の時計・固定データ・一時DBを用意する。実データをfixtureへ混ぜない。
- GPUIの最小ウィンドウを作り、Windowsビルドを確認する。
- Androidは小さなホストで、描画・日本語入力・キーボード表示・バックグラウンド復帰を早期に検証する。現在のGPUI Kitとモバイル依存には互換性確認が必要で、具体的な状況は[調査資料](architecture.md#androidの成立性)に残している。

完了条件: coreのテストが画面なしで実行できる。WindowsとAndroidの結果を分け、ビルド成功・エミュレーター起動・実機成功を混同しない。Android固有の問題があっても、独立したcore実装は進められる。

### 1. ローカルで一通り使える核

- Task / Event / TimeBlock / 所属先の作成・取得・更新・削除、タスク完了。
- 入力検証、ID、関連整合性、SQLiteマイグレーション、トランザクション。
- 期間別の予定取得、未完了・期限・リストでの絞り込み、日本語タイトルの部分一致を含む基本検索。高度な全文検索は後段にし、日本語を適切に分割できない検索方式へ依存しない。
- アプリケーションの操作APIを通した履歴とUndo / Redo。現在の状態テーブルを正とし、全履歴の再生を起動条件にしない。
- GPUI仮画面から「追加→時間割り当て→完了→Undo→再起動」を操作する。

完了条件: 再起動後もID・内容・関連・時刻が復元される。操作の途中失敗で半端な更新が残らない。古い更新版を使った編集やUndoが、新しい変更を黙って上書きしない。Undo対象は自分の操作に限定し、保存する履歴の範囲と上限を明記する。

### 2. カレンダーとしての正しさとデータの持ち出し

- 終日、日跨ぎ、タイムゾーン、月末、うるう年、夏時間。
- 繰り返しは日次・週次・月次の必要な範囲から始める。規則に該当しない日や夏時間の欠落・重複時刻の扱いを仕様と固定ケースで示す。
- 「今回だけ変更／削除」と「系列全体の変更」を扱う。将来分だけ分割する操作は追加段階で扱いを明記する。
- 繰り返しの展開は指定期間・件数で制限し、無限に全件生成しない。繰り返しタスクと、タスクに紐づく繰り返し作業枠は別に設計する。
- バージョン付きJSONで、タスク・予定・作業枠・関連・繰り返し例外を含む全体の入出力。
- カレンダーのICS入出力を段階的に追加。対応する規則を明示し、非対応の規則を黙って落としたり別の意味へ変えたりしない。ICSをUltraTasks全体の完全バックアップとは扱わない。
- 稼働中のSQLiteの整合したバックアップと、別の保存先への復元・検証。WAL中のDBファイルを単純コピーしない。

完了条件: 境界ケースの期待時刻が固定テストで一致する。全体エクスポートから別DBへ復元し、ID・関連・例外を保てる。重複取り込み・入力不正時に既存データを壊さない。マイグレーション前後と失敗時の復旧を確認する。

### 3. OS連携と仮UIの性能検証

- WindowsとAndroidの仮UIを共通coreへ接続する。AndroidはタッチとOSライフサイクルに合わせた薄いホストを持つ。
- リマインダーの予定を永続化し、OSの通知機構へ橋渡しする。権限拒否、時刻変更、再起動後の再登録、予定変更・削除時の取消を扱う。
- Androidのスリープ中やプロセス終了中の通知は、OSの制約・許可を含めて実機検証する。アプリ内タイマーだけで通知を保証しない。分単位の厳密性が必要かは、この段階の仕様で確認する。
- 下記の最小アニメーションと計測を実装する。見た目の仕上げはユーザー監修の反復として別に進める。

完了条件: 日本語入力中に誤送信しない。DB処理で入力・描画を塞がない。OSの終了・復帰で保存済みデータが失われない。通知について実際に確認した条件と未達条件が分かる。

### 4. 自分の端末間同期とセルフホスト

- ローカル機能はサーバーなしで起動・編集可能なまま、任意の同期先を設定できるようにする。
- まず単一ユーザー・複数端末のサーバーを実装する。配布は単一バイナリとコンテナを候補とし、運用・バックアップ手順も用意する。
- 端末登録、取り消せる認証情報、TLSでの運用、サーバーとクライアントのデータ形式の版管理。
- 操作IDによる重複排除、同期カーソル、切断後の再送、ローカル変更の記録を扱う。ローカル更新と送信待ち記録は原子的に保存する。
- 更新版を照合し、競合があれば両方の内容を残して明示的に解決する。最初から複雑なCRDTを前提としない。
- 削除記録を伝搬し、古い端末が削除済みデータを復活させない。履歴・削除記録の保持期間を決め、期限を超えた端末には再同期を要求する。
- 同期されたリマインダーについて、どの端末で通知するかを設定できる形にする。

完了条件: 2端末でのオフライン編集、同一項目の競合、削除対編集、切断・重複配信・再起動・再同期を検証する。任意の順序で配送しても、解決済みデータが収束する。サーバー復元後にもクライアントが検知・再同期できる。

### 5. MCP、その後に内蔵AI

- 最初のMCP対応は、外部AIクライアントがUltraTasksを検索・操作できるサーバー側を提案する。
- UIと同じ操作APIを通し、入力検証・更新版の照合・履歴・Undo・対象範囲の制限を適用する。
- アプリ起動中のデータ所有とプロセス間接続を決める。別プロセスから制御なしで同じDBへ書き込ませない。ローカル接続から始め、遠隔公開が必要なら認証を含めて別に設計する。
- 検索・作成・編集・完了・時間割り当てを小さいツールに分ける。再試行で同じタスクを重複作成しない。
- 内蔵AIは後段。自然文入力、予定整理、時間割り当て提案を同じAPIへ接続する。モデル提供元、データ送信範囲、ローカルモデルの必要性、変更の自動適用範囲をこの段階で決める。

完了条件: 読み取りのみの接続から更新できない。無効な入力・古い更新版・重複要求を正しく処理し、変更元と結果が追跡できる。AIやMCPが保存・履歴の別経路を作らない。

## 仮UIとアニメーション

仮画面は「タスク一覧＋編集欄＋一日分の予定」で十分。レイアウトと部品を別ファイルにし、選択・編集中・スクロールなどの表示状態をドメインデータへ混ぜない。色・余白・文字サイズ・モーションは一か所の設定から変更する。

アニメーションはGPUIの既存機構で次の2種類だけを提案する。独自アニメーションエンジンは作らない。

| 用途 | 仮値 | 確認すること |
| --- | --- | --- |
| 編集パネルの開閉 | 透明度、150ms | 入力・フォーカスが取り残されないこと |
| 作業枠を移した後の補間 | 位置、200ms | DBの確定処理と描画を分け、連続操作でも破綻しないこと |

時間・曲線・有効無効を一か所で変更できるようにする。動きを減らす設定では補間を省く。完了後に再描画を要求し続けない。仮画面のトグルでアニメーション有無を同条件比較できるようにする。

## 検証と性能の記録

- core: 1千／1万件の固定タスク、指定期間の予定、繰り返し系列を用意し、更新・検索・取り込み・展開を測る。
- GPUI: 同じデータと表示サイズで、操作・スクロール・仮アニメーションの有無を比較する。
- 記録: 端末・OS・表示倍率・リフレッシュレート・release/debug・データ数、測定方法、操作遅延、フレーム時間p95/p99、メモリ、アイドルCPU。
- 60Hzで16.7ms、120Hzで8.3msをフレーム予算の目安とする。達成の判断は実際の基準端末と操作条件を決めてから行う。
- 検証は保存・日付・Undo・同期といった失敗するとデータが壊れる境界を中心にする。実装をなぞるだけのテストや、見た目の好みを固定する大量のテストは増やさない。

最初のレビュー可能な成果物は、**画面なしのcoreテストと、追加→時間割り当て→完了→Undo→再起動ができる簡単なGPUI画面**。同期・通知・AIまで一度に詰め込まず、この一連の正しさを確かめて広げる。

## 後で詰める事項

今の実装計画を止める追加質問はない。通知の厳密性、繰り返しタスクの完了後の扱い、MCPの利用クライアント、内蔵AIの自動適用範囲、実機性能の基準端末、配布ライセンスは、それぞれ具体的な実装や配布に入る時点で確認する。

計画外: 初期のチーム機能、ドキュメント、カンバン、常時の外部カレンダー同期、汎用プラグイン機構。将来の追加に必要な境界は保つが、未使用の機能を先に実装しない。
